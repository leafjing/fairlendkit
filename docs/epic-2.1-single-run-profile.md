# Epic 2.1 — Single-run Data-quality Profile Contract

## Status and scope

This is the normative implementation contract for Epic 2.1. It adds a
renderer-neutral, deterministic profile of one audit run to the Epic 1 layered
validation result. The profile covers missingness, group sizes, anomaly
categories, score and outcome distributions, univariate score outliers, and
data freshness.

The profile is descriptive evidence, not a second validator. It does not change
row eligibility, repeat structural or semantic issues, compare against a
baseline, infer representativeness, detect multivariate anomalies, calculate
fairness metrics, or assert fitness, legality, compliance, or data quality.
Epic 2.2 owns baseline comparison and drift.

## Public API and ownership

`validate_audit_data(data, config)` keeps its Epic 1 name and arguments. On a
successful validation it populates `LayeredValidationResult.profile` with a
frozen, strict `SingleRunProfile`. This field is required on newly produced
results and is optional only when parsing a legacy V1 fixture; deterministic
legacy migration sets it to `null` and must not fabricate observations.

`SingleRunProfile` has:

- `schema_version`: literal `"1.0"`;
- `input_rows`, `eligible_rows`, and `excluded_rows`, equal to the enclosing
  validation result;
- `missingness`: ordered `MissingnessProfile` entries;
- `groups`: ordered `GroupSizeProfile` entries;
- `anomalies`: ordered `AnomalyProfile` entries;
- `score_distribution`: one `NumericDistributionProfile` over eligible scores;
- `outcome_distribution`: ordered `CategoryCount` entries over eligible
  outcomes;
- `outliers`: one `OutlierProfile` over eligible scores;
- `freshness`: one `FreshnessProfile`; and
- `issues`: ordered data-quality `ValidationIssue` values generated by the
  profile.

Profile models reject unknown fields, mutable collections, booleans where an
integer or real number is required, and non-finite numbers. Counts are
non-negative integers. Ratios are finite numbers in `[0, 1]`. Empty strings are
not valid field names, methods, categories, versions, or reason codes.

The enclosing data-quality layer contains exactly the profile's `issues` and
derives its status under the Epic 1.4 rules. Profile issues never appear in
structural, semantic, or analytical-reliability layers. Existing Epic 1 issues,
including `missing_required_value`, `unknown_protected_group`,
`unexpected_category`, and `small_group`, are not copied into this profile.

## Population and weighting rules

Each observation declares `population` as `input` or `eligible`:

- Missingness describes the unchanged input population, before exclusion.
- Group sizes describe both input and eligible populations as separate entries.
- Anomaly categories describe the input population so excluded anomalies remain
  auditable.
- Score distribution, outcome distribution, and score outliers describe the
  eligible population used by later analysis.
- Freshness describes run metadata and therefore has no row population.

All Epic 2.1 counts and distributions are unweighted. If
`sample_weight_column` is configured, later analytical metrics may use it, but
the single-run profile continues to expose physical row counts. Weighted
profiles would require an additive contract with explicit weight totals.

`input_rows == eligible_rows + excluded_rows` remains mandatory. Profile row
counts must reconcile to the applicable population. No profile calculation may
mutate data, exclude a row, or alter an Epic 1 reason count.

## Missingness profile

For every required analysis column, produce one overall entry with:

- `field`, `population="input"`, `group=null`;
- `missing_count`, `total_count=input_rows`; and
- `missing_rate = missing_count / total_count`.

For every required analysis column and every observed non-missing allowed value
of each protected attribute, produce one grouped entry. `group` is the same
typed, sorted attribute map used by `AffectedGroup`; `total_count` is the number
of input rows in that group and `missing_count` is the number missing the
profiled field. Do not create an "unknown" or "missing" synthetic group and do
not coerce labels. Missingness of a protected attribute itself is still visible
in its overall entry.

When `input_rows == 0`, validation fails under Epic 1 and no successful profile
exists. Consequently every emitted missingness denominator is positive. Zero
missingness is explicit (`missing_count=0`, `missing_rate=0.0`), not omitted.

## Group-size profile

For each configured protected attribute and each configured allowed value,
produce separate `input` and `eligible` entries containing:

- `group`: one typed attribute/value mapping;
- `count` and `total_count`;
- `proportion = count / total_count`; and
- `is_reference`, derived from `reference_groups`.

Configured groups with zero rows are retained. An input entry always has a
positive denominator. An eligible entry is produced only after Epic 1 has
established `eligible_rows > 0`, so its denominator is also positive. Epic 2.1
does not create intersectional groups; adding them later requires an explicit
group-definition contract.

Group size below `minimum_group_size` remains the analytical-reliability
`small_group` issue. The profile reports the count but emits no duplicate
data-quality issue.

## Anomaly categories

An anomaly is a condition already identified by the declared Epic 1 contract,
not an inferred outlier or a new category learned from the data. Produce an
`AnomalyProfile` for every applicable condition, including zero-count entries:

- `missing_required_value`;
- `unknown_protected_group`;
- `unexpected_category`;
- `duplicate_record`; and
- `non_finite_numeric`.

Each entry contains `code`, `population="input"`, `count`, `total_count`, and
`rate`. Its count must equal the corresponding Epic 1 `reason_counts` value, or
zero when that code is absent. Counts are multi-label: a row may contribute to
several anomaly categories, so their sum need not equal `excluded_rows`.

These entries are evidence only and do not create issues. A condition governed
by an `error` policy still prevents a successful profile; a condition governed
by `exclude` or `allow` remains owned by its existing Epic 1 issue and code.

## Score distribution

The eligible score distribution contains:

- `field`, `population="eligible"`, and `count=eligible_rows`;
- `minimum`, `maximum`, `mean`, `standard_deviation`;
- `quantiles` at exactly `0`, `0.25`, `0.5`, `0.75`, and `1`; and
- `method="linear_type7"`.

Calculations use finite numeric eligible scores converted to binary64. Mean and
population standard deviation use a documented stable two-pass calculation;
standard deviation divides by `count`, not `count - 1`. Quantiles use Hyndman
and Fan type 7 linear interpolation: for sorted zero-based values, position is
`(n - 1) * p`, with linear interpolation between the surrounding values.
For one eligible row, minimum, maximum, mean, and all quantiles equal that score
and standard deviation is `0.0`.

Floating-point serialization follows Python's JSON-safe shortest round-trip
representation. Negative zero must serialize as `0.0`. Implementations must not
round displayed or stored values inside the result model.

## Outcome distribution

For every observed eligible outcome value, emit one `CategoryCount` containing
typed `value`, `count`, `total_count=eligible_rows`, and
`proportion=count/eligible_rows`. Values retain their types; `true`, `1`, and
`"1"` are distinct. Counts sum exactly to `eligible_rows`, and proportions are
computed from those counts.

Entries use the canonical typed-value order defined under determinism. Epic 2.1
does not impose a binary outcome, invent an "other" bucket, or omit infrequent
values. The configured favorable label is not renamed or moved to the front.

## Score outliers

Epic 2.1 uses one deterministic univariate rule:

- `method="tukey_1_5_iqr"`;
- `q1` and `q3` are the score distribution's type-7 quantiles;
- `iqr = q3 - q1`;
- `lower_fence = q1 - 1.5 * iqr`;
- `upper_fence = q3 + 1.5 * iqr`; and
- an outlier is strictly below the lower fence or strictly above the upper
  fence. Values equal to a fence are not outliers.

The result contains lower, upper, and total outlier counts plus eligible total
and outlier rate. If `iqr == 0`, values different from the common quartile are
still classified by the same strict fence rule; the method is not disabled.
Raw score values, row indices, and record identifiers are never serialized.

When at least one outlier exists, emit the warning `score_outliers_observed`.
Its evidence requires `count`, `total`, `minimum` as the lower fence, and
`maximum` as the upper fence. The issue affects only `score_column`, is
non-blocking, and does not imply invalidity or exclusion.

## Data freshness

Freshness uses only `AuditConfig.data_as_of` and `execution_timestamp`. It has:

- `status`: `available`, `unavailable`, or `future_dated`;
- the two timestamps serialized in UTC with a `Z` suffix when available;
- `age_seconds`: whole elapsed seconds, or `null`; and
- `reason_code`: stable code or `null`.

If `data_as_of` is `null`, status is `unavailable`, age is `null`, and emit the
info issue `data_freshness_unavailable`. If `data_as_of` is later than execution
time, status is `future_dated`, age is `null`, and emit the warning
`data_as_of_after_execution`. Otherwise status is `available` and
`age_seconds = floor(execution_timestamp - data_as_of)` in UTC.

Epic 2.1 defines no universal stale-age threshold. Available data of any age
therefore emits no staleness warning. A future policy threshold must be explicit
configuration and an additive contract; it must not silently reinterpret this
profile. Dataset and model version availability remains visible in run context
and is not a freshness proxy.

## Stable data-quality reason codes

The Epic 1.4 issue registry is extended with:

- `score_outliers_observed`: warning, non-blocking, required evidence `count`,
  `total`, `minimum`, `maximum`;
- `data_freshness_unavailable`: info, non-blocking, no evidence values; and
- `data_as_of_after_execution`: warning, non-blocking, required evidence
  `observed` (`data_as_of`) and `expected` (`execution_timestamp`).

Messages are respectively:

- "Eligible scores include values outside the declared Tukey fences."
- "Data freshness was not evaluated because data_as_of is unavailable."
- "data_as_of is later than execution_timestamp."

`comparison_baseline_unavailable` is not emitted by a single-run profile. It is
reserved for a requested comparison whose baseline is unavailable. Until Epic
2.2 is invoked, absence of a baseline is not an attempted check and must not
make the Epic 2.1 data-quality layer `not_evaluated`.

The profile is evaluated when produced. Its data-quality layer is `warning` if
either warning is present, otherwise `not_evaluated` only when freshness is
unavailable and no other profile issue exists, otherwise `passed`. The
`data_freshness_unavailable` info issue is the required explanation for that
`not_evaluated` state. Missing freshness does not erase successfully calculated
profile observations.

## Determinism, privacy, and serialization

Equivalent validated inputs must serialize identically under row permutation,
mapping insertion order, pandas index values, and timezone-offset spelling.
Ordering is:

1. missingness by field, then overall before grouped, then typed group key;
2. groups by attribute, typed value, then `input` before `eligible`;
3. anomalies by code;
4. outcome categories by typed value; and
5. issues under the Epic 1.4 issue order.

A typed value key is `(type rank, canonical value)`, where ranks are boolean,
integer, string. Booleans order `false`, `true`; integers numerically; strings by
Unicode code point. Configuration already restricts labels to these types.

Profile output must not contain row indices, record IDs, raw samples, raw
unknown categories, free-form payloads, or per-row flags. Group and outcome
labels are allowed because they are declared or required audit semantics. No
histogram bins are included in Epic 2.1; the fixed quantiles and complete typed
outcome counts avoid data-dependent bin instability.

JSON round trips preserve types and meaning. Profile schema and generated JSON
must reject unknown fields and non-finite numbers. The canonical Epic 1
applicability statement remains required and renderers must not turn profile
issues into approval, compliance, causation, or remediation claims.

## Compatibility and failure behavior

- All Epic 1.1–1.4 public names, arguments, enums, reason codes, properties,
  exception attributes, and layer ordering remain compatible.
- A successful newly generated result always has a complete profile; profile
  construction cannot return a partial profile.
- Structural or semantic failure still raises `DataValidationError` and returns
  no plausible partial success result or profile.
- Profile invariant failure is an implementation error and must fail closed; it
  must not silently omit a section or serialize non-finite evidence.
- `AuditResult.schema_version` remains `"1.0"` because this is an additive field
  before a released renderer contract. Any later removal or reinterpretation
  requires a schema-version change and migration notes.

## Acceptance tests

Implementation is acceptable only when named automated tests demonstrate:

1. A complete profile is attached to successful validation and row counts agree
   with the enclosing result; legacy V1 fixtures migrate to explicit `null`.
2. Overall and grouped input missingness include explicit zeros, typed groups,
   and exact counts/rates without synthetic missing or unknown groups.
3. Every configured group, including zero-count groups, has separate input and
   eligible counts, proportions, and correct reference designation.
4. All five anomaly categories are present, reconcile with Epic 1 reason counts,
   preserve multi-reason semantics, and create no duplicate layer issues.
5. Score minimum, maximum, mean, population standard deviation, fixed type-7
   quantiles, singleton behavior, and negative-zero normalization match
   hand-calculated fixtures.
6. Outcome counts preserve typed labels, sum to eligible rows, retain rare
   values, and use canonical typed ordering.
7. Tukey fences, strict boundary behavior, zero-IQR behavior, lower/upper/total
   counts, and `score_outliers_observed` evidence match hand calculations.
8. Freshness covers UTC normalization, whole-second age, unavailable
   `data_as_of`, and future-dated metadata with the exact stable issues.
9. The data-quality layer contains exactly profile issues, uses derived Epic 1.4
   status, and never emits `comparison_baseline_unavailable` without a requested
   comparison.
10. Row permutation, mapping insertion order, pandas index, and equivalent
    timezone offsets produce byte-equivalent canonical JSON.
11. Strict models reject booleans as numbers, negative counts, invalid ratios,
    non-finite numbers, unknown fields, raw identifiers, and inconsistent totals
    or derived statistics.
12. All Epic 1.1–1.4 tests and AuditResult schema/round-trip fixtures pass on
    Python 3.11/3.12, and `git diff --check` passes.

The implementation PR must map every criterion to at least one named automated
test. Contract changes require matching documentation and tests. Epic 2.2 must
not start until Epic 2.1 is implemented, independently reviewed, merged, and
green on `main`.
